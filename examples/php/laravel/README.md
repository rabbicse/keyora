# Laravel example

A small notes API protected by Keyora, written with Laravel. It shows the two things an
application has to do:

- call Keyora's REST API from the server (register, login, refresh, logout, introspection);
- verify the access token (an RS256 JWT) locally and check its roles and permissions,
  here as route middleware.

This directory does not contain a whole Laravel application. A fresh Laravel skeleton is
about 80 generated files that have nothing to do with Keyora, so only the integration
files are kept here. The `Dockerfile` and `install.sh` create the skeleton and copy
these files over it. To use them in your own application, copy the same files.

| File | Purpose |
|---|---|
| `config/keyora.php` | Reads the environment variables. |
| `app/Services/KeyoraClient.php` | HTTP client for Keyora's API (Laravel `Http`, HTTP Basic client credentials). |
| `app/Services/KeyoraTokenVerifier.php` | Token verification with `firebase/php-jwt`, plus the `iss`, `aud` and `token_use` checks. |
| `app/Http/Middleware/KeyoraAuthenticate.php` | Middleware `keyora.auth`: a valid token is required. |
| `app/Http/Middleware/KeyoraPermission.php` | Middleware `keyora.permission:<name>[,<name>]`: all listed permissions are required. |
| `app/Http/Middleware/KeyoraRole.php` | Middleware `keyora.role:<name>[,<name>]`: one of the listed roles is required. |
| `app/Exceptions/KeyoraAuthException.php`, `KeyoraUnavailableException.php` | Render `401`/`403` and `502` in the error shape of the examples. |
| `app/Http/Controllers/NotesApiController.php` | The route handlers. |
| `routes/api.php` | The routes and which middleware protects them. |
| `bootstrap/app.php` | Registers the routes at the root (no `/api` prefix), the middleware aliases and JSON error rendering. Replaces the skeleton's file. |

Versions used when this example was last verified: PHP 8.3.37, Laravel 13.43.0,
firebase/php-jwt 7.2.2.

## Prerequisites

- A running Keyora and the `examples/.env` file written by `examples/setup.sh`.
  See [examples/README.md](../../README.md) for both steps.
- Either Docker, or PHP 8.3 or newer with Composer 2. A local PHP needs the extensions
  Laravel itself requires (`php -m` should list `ctype`, `curl`, `dom`, `fileinfo`,
  `filter`, `hash`, `mbstring`, `openssl`, `pcre`, `pdo`, `session`, `tokenizer`, `xml`)
  and `pdo_sqlite`, which the Laravel installer uses once while creating the project.

## Installation

With Docker, build the image from the repository root. The build downloads Laravel and
takes a minute or two the first time:

```sh
docker build -t keyora-example-php-laravel examples/php/laravel
```

With a local PHP and Composer:

```sh
cd examples/php/laravel
./install.sh
```

`install.sh` runs `composer create-project "laravel/laravel:^13.0" build`, then
`composer require "firebase/php-jwt:^7.0"`, copies the integration files into `build/`
and sets `CACHE_STORE=file`, `SESSION_DRIVER=array` and `QUEUE_CONNECTION=sync` in
`build/.env`. `APP_KEY` is generated by `create-project`. The `build/` directory is
ignored by git.

## Configuration

The example reads its settings from environment variables (or from the Laravel `.env`
file of the assembled application).

| Variable | Default | Meaning |
|---|---|---|
| `KEYORA_URL` | `http://localhost:8080` | Where this application reaches Keyora (API calls and JWKS). |
| `KEYORA_ISSUER` | value of `KEYORA_URL` | The `iss` value required in tokens. Must equal Keyora's own issuer setting. |
| `KEYORA_CLIENT_ID` | none, required | The application's client ID. Also the `aud` value required in tokens. |
| `KEYORA_CLIENT_SECRET` | none, required | The application's secret. Server-side only. |
| `PORT` | `9009` | Port to listen on (used by the Docker image; with a local PHP you pass `--port`). |
| `CACHE_STORE` | `file` | Laravel cache store. Holds the JWKS and the example's notes. Any store works; `file` needs no database. |
| `SESSION_DRIVER` | `array` | The routes are stateless and never start a session; `array` makes sure no session table is needed. |
| `PHP_CLI_SERVER_WORKERS` | `4` in the Docker image | Worker processes of the development server. |

No database, session or CSRF token is used. `bootstrap/app.php` registers only the
stateless `api` route group.

## How to run

### With Docker

Inside a container, `localhost` is the container itself, so Keyora on your machine is
reached at `host.docker.internal`. Tokens still say `iss = http://localhost:8080`, which
is why `KEYORA_ISSUER` is set separately. From the repository root:

```sh
docker run --rm --name keyora-example-php-laravel -p 9009:9009 \
  --env-file examples/.env \
  -e KEYORA_URL=http://host.docker.internal:8080 \
  -e KEYORA_ISSUER=http://localhost:8080 \
  keyora-example-php-laravel
```

On Linux, add `--add-host=host.docker.internal:host-gateway`.

### With a local PHP

After `./install.sh`:

```sh
set -a; . ../../.env; set +a        # from examples/php/laravel
cd build
php artisan serve --port=9009 --no-reload
```

`--no-reload` matters here: without it, `artisan serve` starts the server process with
only the values from the `.env` file in `build/` and drops the variables exported in
your shell. The alternative is to copy the four `KEYORA_*` lines into `build/.env` and
omit the flag.

`php artisan serve` runs PHP's built-in development server. It is not a production
server; deploy a real Laravel application behind PHP-FPM, FrankenPHP or Octane.

### Check it

```sh
python3 examples/verify.py http://localhost:9009
```

It should end with `35 passed, 0 failed`.

## Example API requests

Register a user and sign in:

```sh
curl -s -X POST http://localhost:9009/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"ada@example.com","password":"correct horse battery staple","name":"Ada"}'
```

```json
{"id":"ac30c4ed-a6c0-4992-ba02-221d569da7fc","tenant_id":"9276cb35-e993-4b32-a25c-a52306b98780","email":"ada@example.com","name":"Ada","status":"active","email_verified":false,"created_at":"2026-11-23T15:14:38.812Z","updated_at":"2026-11-23T15:14:38.812Z"}
```

```sh
curl -s -X POST http://localhost:9009/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"ada@example.com","password":"correct horse battery staple"}'
```

```json
{"access_token":"eyJhbGciOiJS...","token_type":"Bearer","expires_in":60,"refresh_token":"kyr_sQZ_IKf3...","refresh_expires_in":2591999,"session_id":"0c21bb97-2906-4d22-a377-56951fe800da","user":{"id":"ac30c4ed-...","email":"ada@example.com","name":"Ada","status":"active"}}
```

Keep the two tokens in shell variables for the next requests:

```sh
ACCESS=eyJhbGciOiJS...     # access_token from the login response
REFRESH=kyr_sQZ_IKf3...    # refresh_token from the login response
```

Call a protected endpoint. The token is verified locally:

```sh
curl -s http://localhost:9009/me -H "Authorization: Bearer $ACCESS"
```

```json
{"sub":"ac30c4ed-a6c0-4992-ba02-221d569da7fc","email":"ada@example.com","roles":[],"permissions":[]}
```

A new user has no roles, so the permission middleware refuses the request with `403`:

```sh
curl -s http://localhost:9009/notes -H "Authorization: Bearer $ACCESS"
```

```json
{"error":{"code":"forbidden","message":"missing permission: notes:read"}}
```

Grant the `editor` role with Keyora's admin API (this call goes to Keyora, not to the
example; the IDs are in `examples/.env`, the user ID is `id` from the register response),
then refresh to get a token that contains the new role:

```sh
set -a; . examples/.env; set +a
curl -s -X PUT -H "Authorization: Bearer $KEYORA_ADMIN_KEY" \
  "http://localhost:8080/api/v1/tenants/$KEYORA_TENANT_ID/users/<user id>/roles/$KEYORA_EDITOR_ROLE_ID"

curl -s -X POST http://localhost:9009/refresh \
  -H 'Content-Type: application/json' -d "{\"refresh_token\":\"$REFRESH\"}"
```

The refresh response has the same shape as the login response. Update `ACCESS` and
`REFRESH` from it (the old refresh token is now used up), then:

```sh
curl -s -X POST http://localhost:9009/notes -H "Authorization: Bearer $ACCESS" \
  -H 'Content-Type: application/json' -d '{"text":"buy milk"}'
```

```json
{"text":"buy milk","author":"ada@example.com"}
```

```sh
curl -s http://localhost:9009/notes -H "Authorization: Bearer $ACCESS"
curl -s http://localhost:9009/reports -H "Authorization: Bearer $ACCESS"
curl -s http://localhost:9009/me/live -H "Authorization: Bearer $ACCESS"
```

```json
{"notes":[{"text":"Welcome to Keyora","author":"system"},{"text":"buy milk","author":"ada@example.com"}]}
{"total_notes":2}
{"sub":"ac30c4ed-a6c0-4992-ba02-221d569da7fc","email":"ada@example.com","roles":["editor","reader"],"permissions":["notes:read","notes:write"]}
```

(The last line was observed for a user who had been granted both the `reader` and the
`editor` role.)

Sign out. The answer is `204` with no body:

```sh
curl -s -i -X POST http://localhost:9009/logout \
  -H 'Content-Type: application/json' -d "{\"refresh_token\":\"$REFRESH\"}"
```

```
HTTP/1.1 204 No Content
```

Error responses always have the same shape:

```sh
curl -s http://localhost:9009/me
curl -s http://localhost:9009/me -H 'Authorization: Bearer not-a-token'
curl -s http://localhost:9009/nope
```

```json
{"error":{"code":"missing_token","message":"a bearer access token is required"}}
{"error":{"code":"invalid_token","message":"the access token is malformed"}}
{"error":{"code":"not_found","message":"no such endpoint"}}
```

After the access token's 60 seconds are over, `/me` answers `401` with code
`token_expired`; call `/refresh` to get a new one.

## How it works

**Calls that go to Keyora.** `/register`, `/login`, `/refresh` and `/logout` forward the
JSON body to `POST /api/v1/auth/...` on Keyora, adding the application's
`client_id:client_secret` as HTTP Basic credentials (`KeyoraClient`). Keyora answers
with an envelope, `{"data": ...}` or `{"error": ...}`; the controller returns the `data`
object on success and passes Keyora's status and error code through on failure.
`/me/live` sends the token to `POST /api/v1/auth/introspect` and trusts Keyora's answer;
`active: false` becomes `401 invalid_token`.

The client secret is the reason these calls are made from the server. Never put it in
JavaScript, a Blade view, a mobile app or anything else that is shipped to users. If you
have no server at all, register a `public` application in Keyora instead.

**Checks made locally.** The middleware does not call Keyora per request.
`KeyoraTokenVerifier` checks:

1. The header's `alg` must be exactly `RS256`, and every key is bound to `RS256` when
   the JWKS is parsed (`JWK::parseKeySet`). The token does not get to choose.
2. The signature must verify against the JWKS key whose `kid` matches (`JWT::decode`).
3. `exp` must be present and in the future (`JWT::decode`, which also checks `nbf`).
4. `iss` must equal `KEYORA_ISSUER`.
5. `aud` must equal `KEYORA_CLIENT_ID`. Without this check, a token issued to any other
   application on the same Keyora would be accepted.
6. `token_use` must equal `access`. An OIDC ID token has the same issuer and audience as
   an access token; without this check it would be accepted as one.

`firebase/php-jwt` does not check issuer, audience or token use, so 4 to 6 are explicit code in
the verifier. Do not remove them.

The JWKS is fetched from `${KEYORA_URL}/.well-known/jwks.json` and kept in the Laravel
cache for five minutes (`jwks_ttl` in `config/keyora.php`). If a token names a `kid`
that is not cached, the keys are fetched again (at most once every ten seconds), so a
key rotation in Keyora needs no restart.

**Protecting a route.** The three middleware are registered as aliases in
`bootstrap/app.php`:

```php
->withMiddleware(function (Middleware $middleware): void {
    $middleware->alias([
        'keyora.auth' => KeyoraAuthenticate::class,
        'keyora.permission' => KeyoraPermission::class,
        'keyora.role' => KeyoraRole::class,
    ]);
})
```

and used on routes (`routes/api.php`):

```php
// Any valid token.
Route::get('/me', [NotesApiController::class, 'me'])->middleware('keyora.auth');

// The token must carry every listed permission.
Route::post('/notes', [NotesApiController::class, 'createNote'])->middleware('keyora.permission:notes:write');

// The token must carry at least one of the listed roles ('keyora.role:editor,admin' lists two).
Route::get('/reports', [NotesApiController::class, 'reports'])->middleware('keyora.role:editor');
```

`keyora.permission` and `keyora.role` verify the token themselves, so `keyora.auth` in
front of them is optional. Inside a protected route the verified claims are on the
request:

```php
$claims = $request->attributes->get('keyora.claims');   // ['sub' => ..., 'email' => ..., 'roles' => [...], ...]
```

The example does not use Laravel's `Auth` guards or a `users` table: the token is the
only source of identity.

**Errors.** The middleware throws `KeyoraAuthException`, which renders itself as
`{"error":{"code","message"}}` with status `401` or `403`. `bootstrap/app.php` renders
framework errors (`404`, `405`, unexpected exceptions) in the same shape instead of
Laravel's HTML or `{"message"}` output.

**Local verification or introspection?** Local verification costs no network call but
only learns about a logout or a role change when the token expires or is refreshed.
Introspection sees both immediately and costs one call per request. Compare `/me` and
`/me/live` after a logout.

## Troubleshooting

**Every protected request answers `401 invalid_token`, although login works.** Look at
the `message`:

- `the access token has the wrong issuer`: `KEYORA_ISSUER` differs from the `iss` in the
  token. This is the usual result of running the example in a container: the example
  reaches Keyora at `http://host.docker.internal:8080`, but Keyora signs tokens with its
  own issuer, `http://localhost:8080`. `KEYORA_ISSUER` exists for this case. Set it to
  Keyora's issuer and leave `KEYORA_URL` at the address the container can reach.
- `the access token was issued to another application`: the token's `aud` is not this
  application's `KEYORA_CLIENT_ID`. The token came from a different application, or
  `examples/.env` is out of date (run `examples/setup.sh` again).

To see what a token contains, decode its middle part:

```sh
python3 -c 'import sys,base64; p=sys.argv[1].split(".")[1]; print(base64.urlsafe_b64decode(p+"="*(-len(p)%4)).decode())' "$ACCESS"
```

**`502 identity_unavailable`.** The example cannot reach Keyora at `KEYORA_URL`. Check
that Keyora is running (`curl http://localhost:8080/.well-known/jwks.json`). From a
container, `localhost` does not work; use `http://host.docker.internal:8080` (on Linux
with `--add-host=host.docker.internal:host-gateway`).

**`401 invalid_client` from `/login` or `/register`.** `KEYORA_CLIENT_ID` or
`KEYORA_CLIENT_SECRET` is missing or wrong, so Keyora refuses the application itself.
`examples/.env` is created by `examples/setup.sh`; pass it to Docker with
`--env-file examples/.env`. With a local PHP, remember `--no-reload` (see How to run) or
put the values into `build/.env`. If you ran `php artisan config:cache`, run
`php artisan config:clear`: a cached configuration ignores later environment changes.

**`403 forbidden` on `/notes` or `/reports`.** The user has no role yet. Grant one with
the admin API, then call `/refresh` (roles are copied into the token when it is issued,
so the old token still has none):

```sh
curl -X PUT -H "Authorization: Bearer $KEYORA_ADMIN_KEY" \
  "$KEYORA_URL/api/v1/tenants/$KEYORA_TENANT_ID/users/<user id>/roles/$KEYORA_READER_ROLE_ID"
```

`reader` gives `notes:read`; `editor` gives `notes:read` and `notes:write` and satisfies
`/reports`.

**`401 token_expired` sooner or later than expected, or tokens refused right after
login.** The clocks of this machine and of Keyora disagree. Synchronise them (NTP). If
a small difference is unavoidable, set `leeway` in `config/keyora.php` to a few seconds;
keep it small.

**`500 internal_error`.** Something unexpected failed. The details are in the log
(`storage/logs/laravel.log`, or the container output with `docker logs`). Set
`APP_DEBUG=true` to get the exception message in the response while developing.

**The routes answer under `/api/...` or not at all in your own application.** The
example registers `routes/api.php` with `apiPrefix: ''` in `bootstrap/app.php`. In your
own application keep whatever prefix you already use; the middleware does not depend
on it.

**Requests hang while another one is running.** PHP's built-in server handles one
request at a time. Set `PHP_CLI_SERVER_WORKERS=4` and use `--no-reload` (the Docker
image does both).
